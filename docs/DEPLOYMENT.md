# Deployment

Production runs on four services (plan §0.4, §24):

| Part                   | Service                                           | Config in this repo  |
| ---------------------- | ------------------------------------------------- | -------------------- |
| Website (static build) | Vercel                                            | `client/vercel.json` |
| API (Express)          | Render                                            | `render.yaml`        |
| Database               | MongoDB Atlas                                     | —                    |
| Media                  | Cloudinary (folder `roman-budhathoki/production`) | —                    |

The browser only ever talks to the website's own address: Vercel forwards `/api/*` to Render (`client/vercel.json`),
so the sign-in cookie is first-party.

**Order matters.** The website's build reads content from the API to write link previews and the sitemap, and it
fails if the API answers with an error. So: database → seed content → API → website.

## 1. Production database (Atlas)

Use a separate database (and user) from development, so testing can never touch live data.

1. **Database Access → Add New Database User**: username `roman-prod`, password _Autogenerate_ (copy it), role
   _Specific privileges → readWrite_ on database `roman-budhathoki-prod`.
2. **Network Access → Add IP Address → Allow access from anywhere** (`0.0.0.0/0`). Render has no fixed outgoing
   addresses; the database password is the protection.
3. **Database → Connect → Drivers**: copy the `mongodb+srv://` string, put in the user and password, and add the
   database name before the `?`:
   `mongodb+srv://roman-prod:<password>@cluster0.xxxxx.mongodb.net/roman-budhathoki-prod?retryWrites=true&w=majority`

## 2. Production content (run locally, once)

Create `server/.env.production` (git ignores it) from this template, then run the seeds from the repository root.

```ini
NODE_ENV=production
MONGODB_URI=<the production string from step 1>
# Only needed on machines whose Node DNS can't resolve Atlas (this one): see server/.env.example.
DNS_SERVERS=8.8.8.8,1.1.1.1
CLIENT_ORIGINS=https://example.invalid
JWT_ACCESS_SECRET=<any 32+ characters; only used to satisfy the config check here>
IP_HASH_SALT=<any 16+ characters>
CLOUDINARY_CLOUD_NAME=<same as development>
CLOUDINARY_API_KEY=<same as development>
CLOUDINARY_API_SECRET=<same as development>
CLOUDINARY_ROOT_FOLDER=roman-budhathoki/production
```

```bash
cd server
npx tsx --env-file=.env.production src/scripts/sync-indexes.ts
ADMIN_SEED_PASSWORD='<a strong password>' npx tsx --env-file=.env.production src/scripts/seed-admin.ts --email <owner email> --name "<name>"
npx tsx --env-file=.env.production src/scripts/seed-content.ts
```

`seed-content` uploads the source photos and MP3 to the production Cloudinary folder and creates the profile from the
CV, with gallery photos and the track as drafts.

## 3. API (Render)

1. Render → **New → Blueprint** → choose this GitHub repository. Render reads `render.yaml`.
2. Fill in the values it asks for:
   - `MONGODB_URI`: the production string from step 1.
   - `CLIENT_ORIGINS`: the website's address, e.g. `https://romanviolin.vercel.app` (update it later if Vercel
     gives a different one, or when a custom domain is added).
   - `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET`.
     (`JWT_ACCESS_SECRET` and `IP_HASH_SALT` are generated by Render.)
3. **Apply**. When the deploy finishes, open `https://<service>.onrender.com/api/health`: it should say
   `"status":"ok"` and `"db":"up"`.

   The build ends by syncing the database indexes (once per deploy; a failure stops the deploy), and the service
   starts with `node server/dist/server.js`. If the service was set up by hand rather than from the Blueprint,
   copy the **Build Command** and **Start Command** from `render.yaml` into Settings.

4. If the service address isn't `https://roman-budhathoki-api.onrender.com`, update the `/api` rewrite in
   `client/vercel.json` and push.

## 4. Website (Vercel)

1. Vercel → **Add New → Project** → import this GitHub repository.
2. **Root Directory: `client`**. Leave the framework and build settings alone: `client/vercel.json` sets the install
   command (at the repository root, for the npm workspaces), the build command and the output folder.
3. **Environment Variables** (Production):

   | Name                         | Value                                                                          |
   | ---------------------------- | ------------------------------------------------------------------------------ |
   | `VITE_CLOUDINARY_CLOUD_NAME` | the Cloudinary cloud name (public by design)                                   |
   | `VITE_SITE_URL`              | the website address, e.g. `https://romanviolin.vercel.app`                     |
   | `VITE_API_BASE_URL`          | `/api`                                                                         |
   | `SEO_BUILD_API_URL`          | `https://<service>.onrender.com/api` (build time only, never sent to browsers) |

4. **Deploy**. On a free Render instance the build may wait up to a minute while the API wakes up.

### Cold starts on the free plan

A free Render instance sleeps after 15 minutes without requests, and the next request waits while it starts (often
30–60 s). The website handles this: after 3.5 s it shows a "Tuning up…" notice, and it keeps retrying page data for
up to 100 s before offering "Try again". To avoid the wait entirely:

- **Paid instance** (`plan: starter` in `render.yaml`): never sleeps.
- **Keep-warm ping**: an uptime monitor (e.g. UptimeRobot, every 5–10 minutes) on `https://<site>/api/health`. Free
  instances share 750 hours a month per Render workspace, and one service kept awake all month uses about 744, so
  pinging 24/7 can suspend your other free services near the end of the month. Pinging only during the hours
  visitors come (e.g. 07:00–23:00 Nepal time) uses about 500.

## 5. Checks after the first deploy

- `https://<site>/api/health` answers through Vercel (`"db":"up"`).
- Sign in at `/admin/login`, reload the page: still signed in (the refresh cookie is first-party).
- Publish the drafts in the admin; they appear on the site. Changing the profile's SEO fields or share image needs a
  new Vercel deploy (Deployments → Redeploy) to reach link previews.
- Send a test message through the contact form; it arrives in the admin inbox.
- [securityheaders.com](https://securityheaders.com) on the site: grade A or better.
- Lighthouse (`npm run lighthouse -- https://<site>`) with real content.

## Later: a custom domain

Add the domain in Vercel (Settings → Domains), then update `VITE_SITE_URL` (Vercel) and `CLIENT_ORIGINS` (Render) and
redeploy both. The API needs no domain of its own: the website forwards `/api` to it.
